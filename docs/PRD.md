# agent-harness-wiki 产品需求文档（PRD）

- 文档版本：0.1.0
- 项目名称：agent-harness-wiki
- 项目状态：设计阶段，待初始化
- 文档定位：产品范围、数据契约、系统边界、实现阶段与验收标准
- 配套文件：仓库根目录 `AGENTS.md`
- 首要原则：证据驱动、版本明确、条件完整、更新可追溯、查询可复现

---

## 1. 产品概述

### 1.1 一句话定义

agent-harness-wiki 是一个面向 AI coding agent 及其他 agent harness 的、证据驱动的配置与扩展能力知识库。

项目持续跟踪各 harness 的源码仓库、发布包、二进制和官方文档，将调查结论整理为标准化、带版本与适用条件、可追溯来源的结构化事实，并通过文档站、CLI 和只读 MCP Server 提供查询。

### 1.2 核心问题

当前不同 agent harness 的配置与扩展机制存在明显差异，同一产品的不同形态、版本、分发渠道和运行环境也可能具有不同的行为。

典型问题包括：

- Skills 放在哪里，如何发现，是否递归扫描，同名文件如何覆盖。
- MCP 配置写在哪个文件，支持哪些传输与认证方式，如何验证连接状态。
- 是否支持 custom agents，子代理能否单独配置模型、供应商和工具权限。
- 是否支持 custom providers，配置入口、协议要求、模型元数据和参数转发机制是什么。
- Hooks 有哪些生命周期事件，什么条件下触发，能否阻断操作。
- 是否有原生插件机制，如何安装、更新、探测版本及确认实际加载。
- 全局配置、项目配置、环境变量、profile、CLI 参数和组织策略如何共同决定最终行为。
- 某个结论针对哪个版本，是否仍适用于当前安装版本。
- 上游代码、发布包和官方文档相互矛盾时，应如何表达。

仅整理自然语言文档，容易出现以下问题：

1. 结论缺少明确的版本和环境边界。
2. 官方文档、源码实现和运行行为被混为一谈。
3. “没有查到”被错误地表述为“不支持”。
4. 上游更新后无法确定哪些文档需要重新检查。
5. 同一事实在多个页面中重复维护，逐渐产生不一致。
6. 查询结果缺少证据，调用方 agent 无法判断可靠程度。
7. 自动更新只刷新页面时间，却没有重新验证结论。
8. 最新版本尚未调查，却被旧版本结论隐式覆盖。

本项目需要系统性解决这些问题，而不是只扩大文档数量。

### 1.3 产品定位

本项目由三个核心部分组成：

1. **结构化配置事实库**
   保存具有版本、环境、条件和证据约束的知识。

2. **受控调查与增量更新流水线**
   发现上游变化，评估影响，执行局部调查、验证和审核。

3. **只读知识发布与查询服务**
   将已审核事实发布为统一版本的数据集、文档、CLI 查询结果和 MCP 查询结果。

### 1.4 非定位

本项目不是：

- 通用 agent harness。
- 通用多 agent 调度平台。
- 自动修改用户配置的管理工具。
- 跨 harness 的统一插件安装器。
- 基于全网抓取的泛化搜索引擎。
- 依靠聊天记录或向量相似度决定事实的问答系统。
- 无需审核即可自主发布结论的研究 agent。
- 用于执行任意上游代码或用户脚本的远程执行服务。

## 2. 目标用户与典型场景

### 2.1 用户角色

| 用户角色 | 主要需求 | 核心输出 |
|---|---|---|
| Harness 使用者 | 查清某项配置如何生效，避免误配 | 配置位置、语法、条件、示例、诊断方法 |
| Coding agent | 为用户配置环境前查询准确知识 | 有结构的事实、版本边界、证据、警告 |
| 工具集成开发者 | 比较不同 harness 的扩展接口 | 标准化对照结果、兼容条件、能力差异 |
| 知识维护者 | 跟踪上游变化并维护结论 | 更新任务、影响分析、候选补丁、审核记录 |
| 社区贡献者 | 补充或修正知识 | 可验证的事实补丁、证据与测试 |
| 项目部署者 | 运行共享查询服务 | 可独立部署的只读 MCP 和发布快照 |

### 2.2 典型用户故事

#### US-01：查找配置入口

作为 harness 使用者，我希望查询某个 CLI 在特定版本和操作系统下的 skills 目录，并同时知道项目目录与全局目录的关系，以便正确配置，而不是只得到一个孤立路径。

#### US-02：判断项目级设置是否生效

作为 coding agent，我希望查询配置优先级、合并规则、信任条件及环境变量覆盖规则，以便解释为什么用户的项目级配置没有生效。

#### US-03：比较自定义供应商能力

作为集成开发者，我希望比较多个 harness 的 custom provider 支持，并区分：

- 配置入口是否存在。
- 请求协议是否兼容。
- 模型发现是否可配置。
- 推理强度等能力元数据是否可表达。
- 对应参数是否实际发送到后端。

不能用一个“支持第三方模型”的布尔值替代上述差异。

#### US-04：查询新版本

作为用户，我希望查询一个刚发布的版本。

如果知识库尚未验证该版本，应明确告知尚未验证，并提供旧版本入口，而不是直接把旧结论当作新结论。

#### US-05：回查历史行为

作为维护者，我希望查询某个旧版本当时的配置行为，也希望查询知识库某次历史发布中的结论，以定位回归问题和知识更正过程。

#### US-06：跟踪局部变化

作为维护者，我希望上游配置加载模块发生变化时，只重新调查可能受影响的配置事实，而不是重新运行整个仓库的所有研究任务。

#### US-07：复核矛盾证据

作为贡献者，我希望提交“官方文档声称支持，但指定版本探针未观察到生效”的证据，并让系统保留冲突，而不是强行选择某一方。

#### US-08：离线使用

作为部署者，我希望在更新 worker 离线时，已发布的 CLI 和 MCP 查询仍可正常工作。

## 3. 产品目标与成功标准

### 3.1 产品目标

| 编号 | 目标 | 判断方式 |
|---|---|---|
| G-01 | 配置事实可追溯 | 实质性已接受结论均有有效证据或明确的调查缺口记录 |
| G-02 | 版本与环境边界明确 | 查询结果不隐式跨版本、平台或产品形态外推 |
| G-03 | 多入口结果一致 | 文档、JSON、CLI 和 MCP 来自同一发布数据 |
| G-04 | 上游变化可管理 | 能定位变化、记录影响并触发受控复核 |
| G-05 | 查询不依赖 LLM | 查询路径不调用模型、不执行研究任务 |
| G-06 | 更新失败不影响可用知识 | 旧发布快照持续可用 |
| G-07 | 贡献可审阅 | 事实、证据、适用条件与更正原因可在 Git 中审阅 |
| G-08 | 成本可控制 | 调查任务具有预算、重试边界和明确终止状态 |

### 3.2 质量指标

项目应优先观察：

- 按 harness、产品形态、版本和主题划分的覆盖率。
- 有直接证据的已接受事实比例。
- 证据定位失效数量。
- 待复核事实数量。
- 尚未调查的新版本数量。
- 未解决冲突数量。
- 从发现更新到完成发布的耗时。
- 每次更新实际重新调查的事实数量。
- 每次更新的模型调用量、token 用量和可获取的成本信息。
- 已发布错误事实的更正数量及原因。
- 查询中出现 `not_verified`、`partial` 和 `ambiguous` 的比例。

不得以页面总数、抓取次数或“最后更新时间”单独代表知识质量。

### 3.3 基本质量底线

以下要求为发布底线：

1. 不以缺少结果证明“不支持”。
2. 不把旧版本事实静默应用于新版本。
3. 不把源码行为静默等同于发布包行为。
4. 不把单一平台探针结果外推到其他平台。
5. 不把安装成功等同于加载、激活或健康状态正常。
6. 不把抓取时间当作事实验证时间。
7. 不将未经审核的候选事实暴露给正式查询。
8. 不允许文档与 MCP 维护独立的配置事实副本。

## 4. 产品范围与阶段划分

### 4.1 阶段定义

本项目区分“初始化完成”和“真实知识库 MVP 完成”。

| 阶段 | 名称 | 目标 |
|---|---|---|
| M0 | 可运行初始化 | 用明确标记的虚构数据验证 schema、构建、查询、MCP 和文档闭环 |
| M1 | 真实知识 MVP | 接入少量真实 harness，完成人工辅助调查、审核和正式发布 |
| M2 | 增量维护 | 实现来源变化检测、影响分析、任务恢复和 ResearchRunner |
| M3 | 增强验证与部署 | 增加隔离探针、跨平台验证、远程 MCP 和更多自动化能力 |

M0 不是生产知识发布，不得把测试数据包装成真实调查结果。

M1 优先研究日常使用频率较高的 Codex CLI、OMP，并补充一个以发布包或官方文档为主要证据的调查对象。

真实对象的官方来源、产品边界和仓库身份必须在接入时核验，不在设计文档中预设未经确认的地址或能力。

### 4.2 MVP 包含

- Harness 身份与来源注册。
- 产品形态、版本、平台和条件建模。
- 六类核心能力与横切配置机制。
- 结构化事实、证据、复核与覆盖记录。
- Git 管理的知识真源。
- SQLite、JSON 和文档构建。
- 五个只读 MCP 工具。
- CLI 查询。
- 对未知、冲突、部分覆盖和未验证版本的明确表达。
- 固定发布快照与可重复构建。
- 人工或人工辅助审核发布。

### 4.3 首版明确不包含

- 自动修改本机或远程机器的 harness 配置。
- 自动安装或卸载真实插件。
- 自动执行任意来源的安装脚本。
- 面向用户的写入型 MCP 工具。
- 无人工介入的高风险事实自动发布。
- 通用自然语言网页问答。
- 必须依赖向量数据库的检索。
- 必须依赖 CodeGraph、OpenViking 或其他长期记忆系统的核心路径。
- 必须使用 LangGraph、Temporal 或其他复杂编排框架。
- 对全部 harness、版本和平台的完整覆盖承诺。

## 5. 知识覆盖维度

### 5.1 Skills

至少支持表达：

| 子维度 | 调查内容 |
|---|---|
| 发现位置 | 用户级、项目级、工作区级、内置目录、可覆盖目录 |
| 路径解析 | home、cwd、project root、配置根目录及环境变量 |
| 扫描规则 | 递归、文件命名、符号链接、忽略规则 |
| 同名处理 | 覆盖、合并、去重、冲突、命名空间 |
| 文件格式 | frontmatter、正文、资源目录、字段约束 |
| 调用方式 | 显式调用、隐式调用、模型是否可主动选择 |
| 扩展字段 | 宿主是否识别某个非通用字段及实际语义 |
| 生效条件 | 项目信任、feature flag、启动入口、配置开关 |
| 重载与诊断 | 是否需重启、如何查看已发现或加载的 skills |

### 5.2 MCP

至少支持表达：

| 子维度 | 调查内容 |
|---|---|
| 配置入口 | 文件位置、作用域、配置键 |
| 配置格式 | JSON、JSONC、TOML、YAML 或其他格式及 schema |
| 参数解析 | command、args、env、变量展开、工作目录 |
| 传输 | 实际支持的传输方式与适用版本 |
| 认证 | token、header、OAuth 或其他机制 |
| 连接控制 | 启用、禁用、重试、超时、信任及授权 |
| 能力暴露 | tools、resources、prompts 等能力的实际可用性 |
| 工具发现 | 动态发现、延迟发现、命名、缓存 |
| 诊断 | 连接成功、工具可见、调用成功分别如何验证 |

项目不将“支持 MCP”视为全部子能力都支持。

### 5.3 Custom agents

至少支持表达：

- 定义文件位置和格式。
- 用户级、项目级及其他作用域。
- Agent 名称、描述及调用条件。
- 主代理、子代理和特殊角色的差异。
- 模型与 provider 覆盖能力。
- 工具白名单、黑名单、权限和沙箱设置。
- 指令继承及覆盖规则。
- 最大并发、递归调用或其他运行约束。
- 显式调用与自动委派方式。
- 原生 agent 与第三方扩展实现的区别。
- 加载、发现及运行态诊断方法。

### 5.4 Custom providers

至少支持表达：

- Provider 定义入口与配置格式。
- 身份认证和 base URL。
- 请求协议与端点形态。
- 模型列表及模型发现方式。
- 模型 ID、别名和路由规则。
- 上下文窗口、输出限制等能力元数据。
- 推理强度、工具调用、视觉和其他能力的元数据。
- 参数在 UI、内部配置和实际请求中的传递关系。
- 流式响应、错误响应和重试要求。
- 原生支持、兼容层、插件扩展或 workaround 的区别。

必须区分：

```text
配置中可以填写
    ≠
客户端识别为可用能力
    ≠
实际向后端发送对应参数
    ≠
后端接受并正确执行
```

### 5.5 Hooks

至少支持表达：

- 事件名称与触发时点。
- 用户级和项目级配置。
- matcher 或过滤条件。
- 输入结构。
- 输出结构。
- 退出码语义。
- 是否能够修改、阻断或继续操作。
- 超时与失败处理。
- 执行环境及工作目录。
- 顺序、并发和重复触发行为。
- 信任与安全限制。
- 运行日志及诊断方法。

### 5.6 原生插件

至少支持表达：

- 插件包格式。
- 安装来源。
- 用户级和项目级安装。
- 版本固定及依赖解析。
- 插件目录与发现规则。
- 启用、禁用、更新、卸载。
- 安装版本与运行版本的探测方式。
- 加载顺序、命名空间、冲突处理。
- 宿主兼容范围。
- 插件间兼容性及限制。
- 原生插件与 Skills、MCP、普通脚本的区别。

必须分别表达以下状态：

```text
installed
enabled
discovered
loaded
active
healthy
```

不要求每个 harness 都能直接探测全部状态；无法探测的部分必须明确记录。

### 5.7 横切配置机制

必须覆盖：

- 配置搜索路径。
- 全局、项目、工作区和组织策略。
- 环境变量、CLI 参数、profile。
- 项目信任状态。
- 配置优先级。
- 对象合并、数组替换、空值及删除语义。
- 按配置键变化的例外规则。
- feature flag。
- 默认值。
- 配置迁移、弃用和兼容行为。
- 重载与重启要求。

不得假设所有配置都能被一个全局线性优先级列表准确描述。

## 6. 领域模型

### 6.1 核心实体

| 实体 | 含义 | 主要存储位置 |
|---|---|---|
| HarnessDefinition | 产品身份、别名、产品关系 | `registry/` |
| SourceDefinition | 官方仓库、文档站、包渠道等来源定义 | `registry/` |
| Target | 产品形态、版本、平台、分发和运行方式组成的调查目标 | 知识记录及索引 |
| SnapshotManifest | 固定输入快照的身份与元数据 | `knowledge/snapshots/` |
| Artifact | 原始源码、网页、包文件、探针日志等内容 | 归档存储 |
| Claim | 带条件和适用范围的结构化断言 | `knowledge/claims/` |
| Evidence | 支持、反驳或限定断言的证据 | `knowledge/evidence/` |
| Assessment | 接受、拒绝、争议、更正、复核记录 | `knowledge/assessments/` |
| CoverageRecord | 某个目标和主题的调查覆盖情况 | `knowledge/coverage/` |
| InvestigationJob | 调查任务及阶段状态 | `jobs.sqlite` |
| KnowledgeRelease | 不可变发布快照 | `releases/` 或部署存储 |

### 6.2 Harness 身份

HarnessDefinition 至少包括：

- 稳定的 `harness_id`。
- 展示名称。
- 别名。
- 已知产品形态。
- 官方来源引用。
- 与其他产品的 fork、上游、发行版或包装关系。
- 当前跟踪策略。
- 是否为虚构测试对象。

产品关系只能用于辅助调查，不能自动继承事实。

例如，fork 与上游之间不能因为共享代码历史就默认拥有相同的插件能力。

### 6.3 Target

Target 至少能够表达：

```text
harness_id
surface
version_identity
distribution
os
arch
execution_mode
```

其中：

- `surface`：CLI、IDE 扩展、桌面应用等。
- `version_identity`：版本号、commit、构建号或其他身份。
- `distribution`：不同发布渠道或分发包。
- `execution_mode`：native、WSL、container、remote 等。

版本字符串必须保留原值。只有明确符合相应规则时才应用 SemVer 比较。

不得把 Windows 原生与 WSL 当作同一运行环境。

### 6.4 Claim

Claim 是最小可审阅的事实断言。

每条 Claim 至少包含：

- `claim_id`：该断言的唯一身份。
- `fact_key`：跨版本对照时使用的语义键。
- `schema_version`。
- 目标选择条件。
- 主题。
- 强类型断言。
- 版本适用范围。
- 生效条件。
- 支持与交付方式。
- 证据引用。
- 复核记录引用。
- 必要的更正或替代关系。

一条 Claim 应保持相对原子性。

例如，“项目 skills 目录”和“是否递归扫描”应能够独立维护，避免一个结论变化迫使不相关事实一起更改。

### 6.5 强类型断言

应使用可区分联合类型，而不是开放的 `value: any`。

断言类型可以包括：

```text
search_path
config_location
config_field
default_value
precedence_rule
merge_rule
capability_support
discovery_rule
invocation_rule
transport_support
authentication_rule
provider_protocol
model_metadata_rule
hook_event
hook_exit_behavior
plugin_lifecycle
diagnostic_method
deprecation_rule
```

不同断言类型应具有各自的字段约束和领域校验。

可预留宿主扩展机制，但扩展必须有命名空间及对应 schema，不得成为绕过标准化的任意 JSON 容器。

### 6.6 示例 Claim

以下仅为虚构数据结构示例，不代表任何真实产品：

```yaml
schema_version: 1

claim_id: demo-open-cli-skills-project-path-1_4_2-linux-r1
fact_key: skills.discovery.project_path
record_kind: fixture

target:
  harness_id: demo-open-cli
  surface: cli
  os: linux
  arch: x64
  execution_mode: native

version_applicability:
  kind: exact
  versions:
    - "1.4.2"

topic: skills.discovery

assertion:
  type: search_path
  scope: project
  path:
    base: project_root
    segments:
      - ".demo"
      - "skills"

conditions:
  all_of:
    - type: workspace_trust
      equals: trusted
    - type: environment_variable
      name: DEMO_SKILLS_DIR
      operator: unset

support:
  availability: supported
  delivery: native

evidence_refs:
  - evidence-demo-project-path-source
  - evidence-demo-project-path-probe

assessment_refs:
  - assessment-demo-project-path-accepted
```

真实 fixture 中的文件、证据、hash 和引用必须实际存在，不能复制占位符后视为通过验收。

### 6.7 路径语义

路径应表达为结构化基准和路径片段，必要时再渲染为字符串。

至少区分：

- `home`
- `project_root`
- `workspace_root`
- `cwd`
- `config_root`
- `installation_root`
- 操作系统特定配置目录
- 明确的环境变量引用

`home` 指 harness 实际运行用户的 home，不是 MCP Server 所在机器的 home。

查询服务不得为了“补全路径”而读取查询者或服务器的真实 home、环境变量或文件系统。

### 6.8 条件表达

条件使用有限、可验证的声明式表达，不执行 JavaScript、shell 或其他代码。

应支持：

- 平台与架构。
- 产品形态。
- 运行方式。
- 项目信任。
- feature flag。
- 配置项值。
- 环境变量是否设置。
- 启动参数或 profile。
- 交付方式或扩展是否安装。

必要条件缺失时，返回条件化结果或要求补充条件，不得静默假定成立。

## 7. 状态、覆盖与版本语义

### 7.1 状态分离

以下维度必须分开：

| 维度 | 示例 |
|---|---|
| 可用性 | supported、unsupported、unknown、not_applicable |
| 交付方式 | native、bundled、external_extension、workaround |
| 证据依据 | documented、source_inspected、runtime_observed |
| 审核状态 | draft、accepted、disputed、rejected |
| 更新状态 | current_for_target、recheck_pending、stale、source_unreachable |
| 调查覆盖 | not_started、partial、complete、blocked |

不得将这些维度压缩成单个置信度分数。

`unknown` 可以由覆盖记录和查询解析产生，不要求为未知状态伪造肯定性证据。

### 7.2 否定结论

“unsupported”必须受到与肯定结论相同甚至更严格的条件约束。

可接受的依据包括：

- 官方明确声明在对应目标下不支持。
- 对应版本存在明确拒绝或禁用逻辑。
- 针对明确行为的受控验证与充分的调查范围说明。

以下情况不足以证明一般性的“不支持”：

- 搜索不到关键词。
- 文档没有提到。
- 一次探针失败。
- 配置文件中暂时没有该字段。
- 模型回答它不知道该功能。

探针失败首先应记录为观察结果，再由调查判断其原因。

### 7.3 版本适用范围

M0 默认支持精确版本与固定 revision。

版本范围、版本集合和变更区间可以后续扩展，但必须具备可审阅的建立依据。

基本规则：

1. 检查过一个版本，不自动适用于未来版本。
2. 检查过源码 commit，不自动证明对应二进制包含该实现。
3. 检查过 stable 渠道，不自动适用于 preview 或其他渠道。
4. 仅当来源绑定和行为连续性具有依据时，才扩大适用范围。
5. “最新”必须以查询所使用的知识发布快照为边界。

### 7.4 必须区分的版本概念

- 上游最新发现版本。
- 某目标与主题最新验证版本。
- 某条事实适用的版本。
- 当前知识库发布版本。
- 当前 schema 和构建器版本。

“某 harness 最新验证版本”不能只给出一个没有主题、平台和产品形态限定的数字。

### 7.5 时间字段

至少分别记录：

```text
upstream_published_at
source_fetched_at
source_changed_at
fact_verified_at
knowledge_published_at
```

重新抓取但未复核结论，只能更新来源采集相关时间。

### 7.6 历史与更正

需要支持两个不同问题：

1. 某个软件版本具有怎样的行为。
2. 某次知识发布当时记录了怎样的结论。

已发布内容不能无痕修改。

更正至少保留：

- 原结论。
- 新结论。
- 更正原因。
- 新证据。
- 复核记录。
- 替代或撤销关系。
- 相关知识发布版本。

不要求首版实现复杂事件溯源数据库。Git 历史、不可变发布快照和结构化更正记录可以共同满足需求。

## 8. 来源与证据需求

### 8.1 来源类型

| 来源 | 固定身份方式 | 主要用途 |
|---|---|---|
| Git 仓库 | repository identity + commit | 检查实现和配置加载逻辑 |
| 发布包 | 包身份 + 精确版本 + 内容 hash | 检查实际分发内容 |
| 二进制 | 构建身份 + 平台 + hash | 静态检查和隔离运行验证 |
| 官方文档 | URL + 内容快照 hash | 官方声明、配置示例和说明 |
| 配置 schema | schema 文件身份 + revision | 字段结构、默认值、校验约束 |
| 运行探针 | artifact + fixture + runner 版本 | 特定条件下的实际观察 |

非官方资料可以用于发现问题或形成调查线索，但默认不能单独成为关键配置结论的正式依据。

### 8.2 源码快照

必须记录：

- 官方来源身份。
- commit SHA。
- 文件路径。
- 原始行号或符号位置。
- 相关片段 hash。
- 快照生成方式。

引用应绑定固定 revision，而不是可移动的分支头。

原始源码行号与提取后文本行号必须区分，不能混用。

### 8.3 发布包与源码绑定

必须表达发布版本与源码 revision 的绑定依据。

绑定可能来自：

- 官方发布元数据。
- 包内构建信息。
- 可复现构建或其他直接验证。
- 尚未验证的关联推测。

没有可靠绑定时，源码证据只能证明对应源码目标的行为，不能直接升级为已发布二进制事实。

内容 hash 用于内容完整性和身份比对，不单独证明来源真实性。

### 8.4 文档快照

必须保存：

- 原始 URL。
- 重定向后的 URL。
- 抓取时间。
- 原始内容 hash。
- 提取内容 hash。
- 标题、段落或其他定位信息。
- 提取器版本。
- 可适用的软件版本信息；未知时明确标记。

原始 hash 必须保留。归一化内容只能用于辅助变化判断，不能掩盖真实代码片段和配置值变化。

### 8.5 Evidence

每份证据至少包括：

- 唯一身份。
- 来源类型。
- 快照引用。
- 定位信息。
- 必要的短摘录或摘录引用。
- 支持、反驳或限定的 claim。
- 采集方法。
- 定位验证状态。
- 公开展示策略。
- 许可及再分发注意事项。

自动校验能够验证“证据位置存在”，不等于能够自动证明“证据支持该结论”。

### 8.6 冲突证据

源码、文档和运行探针之间不设不可变的全局高低顺序。

冲突处理应先检查：

- 是否实际上对应不同版本。
- 是否对应不同分发包。
- 是否遗漏生效条件。
- 是否属于文档声明与运行观察的差异。
- 探针是否测量了正确的行为。
- 是否存在构建开关或发布延迟。

不能消除的冲突必须保留并在查询中展示。

### 8.7 归档与公开发布

原始 artifact 与公开证据分开管理。

原则：

- 不默认把全部源码、网页和包文件提交到主仓库。
- 不默认重新分发闭源包。
- 不默认公开完整探针日志。
- 不在公开产物中包含 token、用户目录、私有地址和其他敏感数据。
- 对支持已接受事实的原始证据采用明确归档策略，不能仅作为随时可清理的临时缓存。
- 公开数据构建不应要求临时访问全部上游来源。

## 9. 调查工作流

### 9.1 首次接入

标准流程：

```text
确认产品身份与官方来源
    → 定义调查目标
    → 获取固定快照
    → 建立主题调查清单
    → 规则提取与人工/Agent 调查
    → 形成候选事实和证据
    → 结构校验
    → 语义复核
    → 必要的运行验证
    → PR 审核
    → 接受事实
    → 构建并发布
```

接入完成不等于所有主题都已确定。

未调查、调查受阻或证据不足的主题应写入覆盖记录。

### 9.2 ResearchRunner 的职责

ResearchRunner 是可替换的调查执行接口。

输入至少包括：

- 固定任务 ID。
- harness 和 Target。
- 需要回答的问题。
- 旧事实及相关证据。
- 输入快照引用。
- 相关 diff。
- 允许访问的材料范围。
- 工具与网络权限。
- 输出 schema。
- 预算和重试边界。

输出至少包括：

- 候选 Claim。
- 候选 Evidence。
- 调查范围。
- 未解决问题。
- 冲突。
- 建议复核项。
- 使用量与执行状态。

ResearchRunner 不得直接修改正式发布数据。

### 9.3 上下文策略

任务包用于聚焦问题，不应成为阻断必要探索的封闭材料包。

研究 Agent 可以在固定、只读的来源快照中：

- 搜索其他相关文件。
- 沿调用关系扩展调查。
- 检查配置解析、加载和运行调用链。
- 请求补充来源快照。

不能未经记录就改用更新后的上游内容，使同一任务混入不同 revision。

### 9.4 模型与执行器分工

允许采用：

- 强模型：首次接入、复杂语义、冲突处理、验收。
- 低成本工作模型：局部变化调查、证据补齐、确定性整理。
- 无模型提取器：schema、配置键、版本元数据等规则提取。

主系统不绑定某个模型厂商或某个 agent CLI。

CodeGraph 可以辅助源码探索；长期记忆工具可以辅助研究过程。二者均不能替代正式证据和结构化知识真源。

### 9.5 修复与终止

每项任务必须具有有限重试次数。

验证失败后，应将问题返回原任务上下文修正，不默认重新发起完整研究。

超过重试上限或存在无法自动解决的问题时，进入 `blocked`，保存已有结果和阻塞原因。

禁止无限循环：

```text
研究 → 验证失败 → 全量重新研究 → 再次失败
```

## 10. 增量更新需求

### 10.1 变化发现

分别跟踪：

- 新发布版本。
- 已跟踪源码 revision 的变化。
- 官方文档内容变化。
- 配置 schema 变化。
- 发布包内容变化。
- 已知来源失效或迁移。

文档更新不依赖软件发布事件。

来源轮询应支持缓存、条件请求、限速、退避和失败记录。轮询频率为配置项，不在代码中写死。

### 10.2 影响分析

建立轻量依赖关系：

```text
源文件 / 符号 / 文档段落 / schema
              ↓
          配置规则
              ↓
            Claim
              ↓
      页面、示例、比较与查询
```

初期使用普通关系表和索引，不引入专用图数据库。

影响分析可以利用：

- 证据指向的文件。
- 主题与模块映射。
- 配置键和 schema 字段。
- 手工维护的核心加载模块。
- 已知跨主题依赖。
- diff 类型。

### 10.3 兜底策略

依赖关系不视为完备证明。

出现以下变化时扩大调查：

- 新增未知模块。
- 配置入口或加载器变化。
- 构建与 feature flag 变化。
- 大规模重构。
- 目录迁移。
- 版本标识或分发机制变化。
- 影响分析无法判断。

系统还应支持按周期执行完整主题复核，用于发现依赖映射遗漏。

### 10.4 未变化内容的处理

源文件未变化可以作为减少调查的依据，但不能机械证明发布包行为不变。

是否允许复用结论取决于：

- Target 是否变化。
- 发布包与源码绑定是否可靠。
- 依赖模块是否变化。
- 生效条件和构建选项是否变化。
- 复核策略是否允许。

复用过程应产生 Assessment，而不是直接刷新验证日期。

### 10.5 任务状态机

建议状态：

```text
discovered
  → snapshotted
  → impact_planned
  → researched
  → validated
  → awaiting_review
  → published
```

异常状态：

```text
failed
blocked
superseded
cancelled
```

要求：

- 每阶段保存产物。
- 失败后可从已完成阶段恢复。
- 并发 worker 不重复发布同一任务。
- 具有幂等键。
- 具有任务租约或其他防重复领取机制。
- 重试不会破坏之前已接受知识。

幂等键应覆盖输入快照、目标、主题、schema、提取器、调查规范和探针版本。

## 11. 运行探针需求

### 11.1 定位

探针用于补充实际运行证据，不用于替代所有源码和文档调查。

M0 使用本地模拟与 fixture；真实探针作为后续阶段实现。

### 11.2 探针类型

| 类型 | 目标 |
|---|---|
| Skills 探针 | 发现目录、同名覆盖、重载 |
| MCP 探针 | 连接、工具发现、调用 |
| Provider 探针 | 请求端点、参数转发、流式处理 |
| Hook 探针 | 事件触发、输入输出、阻断语义 |
| Plugin 探针 | 安装、发现、加载、激活、健康 |
| 配置探针 | 优先级、合并规则、环境变量覆盖 |

### 11.3 探针隔离

必须：

- 使用临时 HOME、XDG、APPDATA 等配置根。
- 使用独立工作目录。
- 不读取用户真实凭据。
- 默认限制网络。
- 设置超时、输出上限和资源限制。
- 使用固定 fixture。
- 记录被测 artifact 和探针版本。
- 对日志进行敏感信息处理。

Provider 探针优先使用本地 mock endpoint，避免无意消耗真实服务额度。

### 11.4 探针结论边界

探针只能证明具体目标与条件下的观察。

不得将：

- Linux 结果外推到 Windows。
- Mock provider 接收参数外推为真实 provider 正确执行。
- 工具列表可见外推为调用成功。
- 安装命令成功外推为插件健康。
- 模型的口头回答视为功能加载的确定性证据。

## 12. 存储与发布架构

### 12.1 四类存储

#### A. Git 知识真源

保存：

- Registry。
- Claim。
- Evidence 元数据。
- SnapshotManifest。
- Assessment。
- CoverageRecord。
- 调查规范。
- 引用事实的解释性文档。

#### B. 原始 artifact 归档

保存：

- 源码快照。
- 文档快照。
- 发布包。
- 二进制。
- 探针日志。
- 调查中间产物。

采用内容寻址或等效的完整性机制。

#### C. 运行状态

`jobs.sqlite` 保存：

- 任务状态。
- 执行阶段。
- 重试次数。
- worker 租约。
- 预算与使用量。
- 产物引用。
- 错误和阻塞原因。

它不是查询事实库。

#### D. 发布产物

每个发布包含：

```text
manifest.json
knowledge.sqlite
knowledge.json
docs/
```

### 12.2 SQLite 的定位

SQLite 是可重建的发布索引，不是知识真源。

任何接受事实的修改必须回到 Git 中的结构化记录。

不得只修改 SQLite 后将其视为有效知识更新。

### 12.3 构建器

构建器负责：

1. 读取固定输入。
2. 校验 schema。
3. 校验跨记录引用。
4. 检查版本、条件和冲突。
5. 解析有效 Assessment。
6. 生成标准 JSON。
7. 生成 SQLite 结构化表与全文索引。
8. 生成 Markdown。
9. 生成 manifest。
10. 验证产物完整性。

构建默认离线，不在构建过程中抓取上游或调用模型。

### 12.4 可重复构建

相同输入、schema、构建器及发布参数应产生：

- 相同的标准 JSON 语义及规范化字节。
- 相同的 Markdown。
- 相同的 SQLite 逻辑内容。

首版不承诺跨 SQLite 引擎版本的数据库文件逐字节一致。

构建时间必须是显式输入或从固定发布元数据派生，不能在任意位置调用当前时间破坏确定性。

### 12.5 发布切换

发布采用不可变目录：

```text
releases/<release-id>/
```

新发布先在 staging 目录完成构建与校验，再切换发布指针。

禁止原地覆盖正在提供查询的 SQLite 文件。

查询进程在切换时：

- 验证新 manifest。
- 验证索引 schema 兼容性。
- 打开新索引。
- 成功后切换。
- 失败时继续使用旧发布。

旧发布的保留与清理必须采用明确策略。

## 13. 查询语义

### 13.1 通用原则

查询只读取已发布知识。

禁止：

- 查询时联网补充事实。
- 查询时调用 LLM 生成新结论。
- 查询时执行上游程序。
- 查询时修改知识数据。
- 在未声明的情况下切换到其他发布版本。

### 13.2 版本策略

支持：

```text
exact
latest_verified
latest_upstream
```

#### exact

只返回明确适用于请求版本的事实。

没有对应事实时，返回 `not_verified` 或部分覆盖，不自动回退。

#### latest_verified

按请求的产品形态、环境和主题选择一个明确版本。

只返回这个版本的事实，不得把各字段在不同版本的最新结果拼成一个不存在的“完整版本”。

如果选定版本只有部分覆盖，返回 `partial`。

#### latest_upstream

使用发布快照中最后观察到的上游版本。

这不是实时联网获取的“此刻最新版本”，必须同时返回观察时间。

尚未验证时返回 `not_verified`。

### 13.3 条件解析

条件不足时：

- 可返回所有明确标注条件的候选结果。
- 或返回 `ambiguous`，指出需要补充的条件。

不得根据 MCP Server 的操作系统、home 或环境变量代替用户指定条件。

### 13.4 结果状态

业务结果至少包括：

```text
ok
partial
ambiguous
not_verified
conflict
not_found
```

技术错误应使用单独错误代码，例如：

```text
INVALID_ARGUMENT
RELEASE_NOT_FOUND
RELEASE_SCHEMA_UNSUPPORTED
INDEX_UNAVAILABLE
CURSOR_RELEASE_MISMATCH
```

“没有调查过”是正常业务结果，不应表现为服务故障。

### 13.5 比较规则

比较必须基于共同 `fact_key` 或明确的主题维度。

要求：

- 每个对象明确显示解析后的 Target。
- 缺失内容显示 unknown 或调查状态。
- 不将缺失单元格视为不支持。
- 不把 native、plugin 和 workaround 合并。
- 不把不同平台或产品形态当作完全可比。
- 不自动提供综合排名。
- 冲突内容保留冲突标记。
- 一个比较结果固定使用同一知识发布版本。

### 13.6 查询示例

以下为虚构响应：

```json
{
  "schema_version": 1,
  "knowledge_release": "fixture-basic",
  "status": "not_verified",
  "resolution": {
    "harness_id": "demo-open-cli",
    "surface": "cli",
    "requested_version": "1.5.0",
    "resolved_version": null,
    "latest_upstream_seen": "1.5.0",
    "latest_verified_version": "1.4.2",
    "reason": "requested_version_not_verified"
  },
  "coverage": {
    "topic": "skills.discovery",
    "state": "not_started"
  },
  "facts": [],
  "fallbacks": [
    {
      "version": "1.4.2",
      "requires_explicit_selection": true
    }
  ],
  "warnings": [
    {
      "code": "NEWER_VERSION_UNVERIFIED",
      "message": "已发现请求版本，但该主题尚未完成复核。"
    }
  ]
}
```

## 14. MCP 产品接口

### 14.1 工具集合

首版固定为五个只读工具：

| 工具名 | 职责 |
|---|---|
| `list_harnesses` | 列出产品、别名、形态、覆盖与版本概况 |
| `get_capability` | 查询某目标下某主题或事实键 |
| `compare_capabilities` | 比较多个目标或版本 |
| `search_knowledge` | 搜索已发布事实和说明 |
| `get_evidence` | 获取已发布证据及定位 |

不为每个 harness 动态生成一组工具。

### 14.2 主要输入

`get_capability` 至少接受：

```text
harness
topic 或 fact_key
surface
platform
execution_mode
version 或 version_policy
conditions
knowledge_release
detail_level
```

其他工具使用一致的目标选择和发布选择语义。

### 14.3 返回内容

结构化结果应包含：

- 请求解析结果。
- 实际 Target。
- 知识发布版本。
- 事实与适用条件。
- 证据引用。
- 覆盖情况。
- 更新状态。
- 冲突和警告。
- 分页信息。

协议适配层提供结构化输出，并在需要时提供相同数据的文本表示。

不得在 MCP 层新增一套独立的回答逻辑。

### 14.4 分页与大小限制

必须设置：

- 默认 limit。
- 最大 limit。
- 证据摘录长度上限。
- 响应体上限。
- 分页 cursor。

Cursor 必须绑定发布版本和查询条件。

旧发布不可用时，不允许悄悄用新发布继续分页。

### 14.5 Resources

可后续暴露：

- Harness 页面。
- Topic 页面。
- 证据记录。
- 发布说明。
- Schema。

Resources 是补充入口，不是五个核心工具的替代。

### 14.6 传输与兼容

M0 实现 stdio。

远程部署阶段实现 Streamable HTTP。

SDK 和协议版本在实际初始化或升级时核验并锁定。不得混用不同主要版本的 SDK 示例。

业务查询与协议适配分离，必要的兼容逻辑限制在 MCP adapter 内。

工具的只读标记属于描述信息，实际只读性仍必须由代码和部署权限保证。

## 15. 搜索需求

### 15.1 检索顺序

优先采用：

```text
产品别名归一化
    → 结构化筛选
    → fact_key、配置键和路径精确匹配
    → 受控全文检索
```

### 15.2 中文与短词

建立受控别名，例如：

```text
钩子 ↔ hook
子代理 ↔ subagent
供应商 ↔ provider
技能 ↔ skill
```

短词、配置键和路径优先使用精确匹配或专门索引。

不假设默认全文 tokenizer 可以可靠处理全部中文和短查询。

### 15.3 搜索结果

每条命中至少返回：

- Claim 或页面身份。
- Harness 和 Target。
- 主题。
- 命中原因。
- 摘要。
- 支持状态或调查状态。
- 证据引用。
- 发布版本。

搜索排序仅用于相关性，不表示事实可信度或产品优劣。

### 15.4 向量检索

不属于 MVP 核心依赖。

未来可用于发现候选材料，但不能绕过版本、环境和条件过滤，不能替代证据和结构化适用性判断。

## 17. 技术架构与选型

### 17.1 推荐技术栈

| 层次 | 选择 |
|---|---|
| 语言 | TypeScript，strict，ESM |
| 运行时 | 初始化时核验并固定的受支持 Node.js LTS |
| 包管理 | pnpm workspace |
| 运行时 schema | Zod |
| 外部 schema | 从主 schema 导出的 JSON Schema |
| YAML | 安全的 YAML 解析库 |
| CLI | Commander 或经 ADR 确认的同类轻量库 |
| 开发执行 | tsx |
| 正式构建 | tsc 或经 ADR 记录的构建器 |
| 查询数据库 | SQLite + better-sqlite3 |
| 全文索引 | SQLite FTS5，配合精确索引与别名 |
| MCP | 官方 TypeScript SDK |
| 文档站 | VitePress |
| 测试 | Vitest |
| 远程采集 | HTTP/Git 适配器；动态页面按需使用浏览器 |
| 更新编排 | 显式状态机 |
| 初始部署 | 单机 worker + 独立只读查询服务 |

依赖版本必须在实施时核验并锁定，不依赖本文对“最新版本”的推测。

### 17.2 逻辑架构

```text
                    维护侧
──────────────────────────────────────────

来源注册
   ↓
Source Connectors
   ↓
固定 Snapshot / Artifact
   ↓
变化检测 + 影响分析
   ↓
规则提取 / ResearchRunner / 探针
   ↓
Candidate Facts + Evidence
   ↓
自动校验 + 语义复核 + PR 审核
   ↓
Git 知识真源
   ↓
离线构建器
   ↓
不可变 KnowledgeRelease

──────────────────────────────────────────
                    查询侧

KnowledgeRelease
   ↓
QueryService
   ├── CLI
   ├── MCP
   └── JSON / 文档站
```

### 17.3 依赖方向

```text
domain
  ↑
validation / compiler / query / sources / research / probes
  ↑
pipeline / cli / mcp
```

要求：

- Domain 不依赖 MCP。
- Query 不依赖 ResearchRunner。
- Query 不依赖网络采集。
- Compiler 不调用 LLM。
- MCP 不直接写知识真源。
- 文档生成与查询共享同一语义模型。
- 各 adapter 不反向决定领域事实的 schema。

### 17.4 包拆分

首版采用主程序包和文档站两个 workspace 单元。

逻辑模块不等于独立 npm package。

没有明确复用或独立发布需求时，不为了形式拆出大量 packages。

## 19. 安全与信任边界

### 19.1 上游内容不可信

README、网页、代码注释和包内文本是研究数据，不是对研究 Agent 的操作指令。

ResearchRunner 不得因为来源内容中的指示：

- 上传凭据。
- 执行任意命令。
- 修改项目规则。
- 修改审核门禁。
- 绕过测试。
- 自动发布。

### 19.2 权限分离

维护 worker、研究执行器、探针和查询服务应分别具备最小权限。

研究执行器可以写候选结果，但不能直接发布。

探针不继承研究执行器的模型凭据。

查询服务原则上只需读取发布目录。

### 19.3 下载与解包

采集与解包需要防范：

- 路径穿越。
- 危险符号链接。
- 超大文件和解压炸弹。
- 非预期重定向。
- 不受信任的协议。
- SSRF。
- 恶意安装生命周期脚本。

静态检查优先，不能为了查看包内容而默认执行包的安装脚本。

### 19.4 文档构建

来源内容进入文档时必须经过受控处理。

不能直接执行上游 MDX、HTML script、Vue 组件或其他活动内容。

### 19.5 远程 MCP

远程模式需要：

- 明确的监听地址。
- Origin 与来源校验。
- 按部署场景设置认证。
- 响应大小和请求频率限制。
- 不泄露内部路径和凭据。
- 明确记录协议兼容范围。

不得为了本地开发方便而默认对公网开放。

## 20. 可观测性、成本与可靠性

### 20.1 任务日志

至少记录：

- job ID。
- 阶段。
- 输入快照。
- 执行器版本。
- 开始、结束和耗时。
- 重试次数。
- 结果状态。
- 错误类型。
- artifact 引用。
- 可获取的模型使用量。

日志不得包含完整凭据或默认记录全部敏感上下文。

### 20.2 预算

研究任务支持：

- 最大并发。
- 最大模型调用次数。
- 最大 token 或成本预算。
- 最大运行时间。
- 最大修复次数。
- 最大输出大小。

无法获取准确成本时应标记未知，不以估算冒充账单。

### 20.3 可靠性

- 更新失败不影响旧发布。
- 发布校验失败不切换当前版本。
- QueryService 不依赖 jobs 数据库可用。
- 来源不可达不等于事实被证伪。
- worker 停止不影响已发布查询。
- 任务取消和重试保留审计记录。

### 20.4 性能

M1 应建立基准数据集并记录：

- 事实与证据数量。
- SQLite 体积。
- 构建耗时。
- 查询冷启动时间。
- 常用查询 P50/P95。
- 搜索 P50/P95。
- MCP 响应体大小。
- 测试机器与软件版本。

性能目标必须基于明确环境，不将未经测量的目标写成已实现能力。

## 21. 测试与验收

### 21.1 M0 验收

M0 必须完成：

1. 项目可安装、类型检查、测试和构建。
2. 至少两个明显虚构的 harness fixture。
3. 六类核心主题均有至少一个强类型示例。
4. 正式数据和 fixture 数据隔离。
5. YAML → 校验 → JSON/SQLite/Markdown 链路运行。
6. CLI 能完成五类查询。
7. MCP stdio 暴露五个固定只读工具。
8. 使用真实 SDK 客户端完成 MCP smoke test。
9. 文档站可构建。
10. README 包含实际可运行命令。
11. 正式查询路径不调用 LLM、不联网。
12. 构建产物可重复生成。
13. 错误输入不会生成假成功产物。

### 21.2 必测语义

至少测试：

| 场景 | 预期 |
|---|---|
| 请求已验证精确版本 | 返回对应事实 |
| 请求未验证新版本 | 不静默使用旧版本 |
| Linux 已验证、Windows 未验证 | Windows 不得到 Linux 结论 |
| 缺少关键条件 | 返回条件化结果或 ambiguous |
| 没有调查记录 | unknown/not_started，而非 unsupported |
| 文档与运行证据冲突 | 返回 conflict |
| 第三方插件实现 | 不标成 native |
| 安装成功但未确认加载 | 不标成 healthy |
| 证据引用不存在 | 校验失败 |
| 源码与发布包未绑定 | 不升级为发布包确定事实 |
| 构建器重复运行 | 规范化内容一致 |
| 新发布损坏 | 旧发布保持可用 |
| 分页跨发布 | 拒绝或要求重新查询 |
| 搜索中文别名和短词 | 返回受控、可解释结果 |
| 上游内容包含恶意指令 | 不执行，不改变权限 |
| Fixture 混入正式发布 | 构建失败 |

### 21.3 M1 验收

除 M0 外：

- 至少两个真实 harness 完成正式接入。
- 官方来源身份已确认。
- 至少一个精确目标版本具备可查询事实。
- 六类主题均有明确覆盖记录，允许诚实的 unknown 或 blocked。
- 已接受实质性结论均可追溯到证据。
- 至少完成一次人工辅助 PR 审核与正式发布。
- 文档和 MCP 对同一事实返回一致的版本、条件和来源。
- 不依赖研究 worker 在线即可查询。

### 21.4 M2 验收

- 能发现至少一种源码变化和一种文档变化。
- 能将变化映射到受影响主题。
- 能只对受影响主题建立调查任务。
- 能恢复失败任务。
- 能限制重试与预算。
- 能保存未解决冲突。
- 能在新版本未验证时维持旧版本服务。

### 21.5 M3 验收

- 至少一种真实隔离探针运行成功。
- 探针结果具备完整 Target 与执行证据。
- 至少两个目标平台的差异不被错误合并。
- 远程 MCP 具备明确认证和访问边界。
- 对实际目标客户端执行兼容测试。

## 22. 风险与设计对策

| 风险 | 对策 |
|---|---|
| 数据模型过度复杂 | M0 先实现精确版本和有限条件，使用真实问题迭代 |
| 数据模型过度简单 | 禁止单一 supportsX 布尔值和任意 value 容器 |
| 调查 Agent 幻觉 | 固定输入、证据定位、语义复核、候选发布隔离 |
| 上游更新太频繁 | 影响分析、缓存、优先级与预算 |
| 文档与代码矛盾 | 保留冲突，不设机械证据排名 |
| 闭源信息不足 | 明确已知边界与 unknown，不强行填满 |
| 维护成本失控 | 少量对象起步，先验证闭环再扩大覆盖 |
| SDK/API 变化 | 适配层隔离、版本锁定、契约测试 |
| Fixture 冒充真实知识 | 显式 record_kind、发布隔离、强制校验 |
| 生成文档分叉 | Claim 为真源，文档由统一构建器生成 |
| 过早基础设施化 | 单机、SQLite、显式状态机优先 |
| 查询服务权限过大 | 只读发布、无研究能力、无执行工具 |

- 默认轮询频率和完整复核周期。
- 是否提供英文文档。
- 哪些低风险变更允许未来自动审核。
- 是否引入专门的浏览器采集器。
- 是否支持外部分布式 worker。

未决事项应进入 ADR 或待办，不应通过任意默认值伪装成已决定。

## 24. 最终产品原则

agent-harness-wiki 的核心价值不是“收集更多文字”，而是持续回答：

> 对哪个产品、哪个版本、哪个环境，在什么条件下，这项配置或能力如何工作；结论来自哪里，是否经过复核，上游变化后它是否仍然适用。

项目的核心资产是：

1. 稳定且可扩展的知识 schema。
2. 可复用的调查和验证规范。
3. 带完整来源与版本边界的事实库。
4. 可重复构建的发布体系。
5. 不会把未知包装成确定答案的查询接口。
