# Design

## Context

动机与规格范围见 [proposal.md](proposal.md)。既有 `chapter-update-workflow` 描述的是维护者手动调用：扫描、调查、采写、发布、受管刷新一次完成。每日巡检要插入「先回答哪些来源变了」这一步，同时不把发布判断交给编排层。

依赖的仓库内命令（`sources:check`、`sources:workspace open`／`close`／`recover`、`monitor:session start`／`finish`、`maintenance:candidates prepare`／`check`／`plan`）与模型验证是启用前提。调度注册本身在编排工具侧完成，Skill 不做编排工具的写入。

## Goals / Non-Goals

**Goals:** 每天给出「哪些登记来源变了、哪些旧审计还没结案」的确定答案；由父进程判断调查必要性，维护子代理调查有证据关联的问题；让改动可被一个持续到合并的 pull request 复核和回退；让来源读取不依赖仓库内的源码副本。

**Non-Goals:** 无人值守的知识发布、自动合并、并发巡检实例、模型可用性回退、巡检期内的受管二进制刷新、自动清理历史原件或审计，以及用巡检替代手动维护的定向调查。

## Decisions

### 编排层判断必要性并协调隔离候选

巡检的价值在于把「变化」变成固定输入，而不是在调度里重写章节语义。父进程比较固定观察、现有问题和必要的来源 diff，判断是否有实质更新线索或可执行的调查入口，记录不需维护的理由。来源失败无修复线索或旧阻塞无新证据时保留 blocked；影响不明先限定入口，不默认重审七章。维护 worker 在 `delivery=pr` 下只调查指定问题。

### 观察范围是 catalog 与 registry 的交集

catalog 里的候选产品没有登记来源，观察它们只会产生「来源缺失」的假失败；registry 里的产品必然在 catalog 声明。交集因此是唯一能同时满足「有来源可观察」和「身份有事实源」的范围。

### 只读观察与手动扫描共享基线

`sources:check` 与 `sources:scan` 读同一基线与审计目录，区别只在是否落盘。这样每日观察看到的 baseline 与维护者手动扫描看到的 baseline 相同，轮次之间可比；只读入口不下载包字节、不创建 clone，避免每天产生无人清理的临时副本。需要落审计的轮次由 `sources:scan` 或维护 Skill 写出。

### 主会话模型来自项目配置，子代理模型显式传入，隔离并行且每产品一次

主会话模型由项目 `.codex/config.toml` 决定。子代理模型不由这份配置隐式继承：每次委派显式传入 `minimax-cn/MiniMax-M3.1-Flash-Preview`，缺参数即视为配置错误，这样模型选择留在编排输入里而不是散落在多处默认值。主 Agent 自行决定并行规模。每个产品一个 worker，在单产品候选中编辑 catalog、来源、章节、选章与审计；主 Agent 汇总 completed 候选，检查 baseline 后生成临时合并数据，通过内置编辑工具统一集成。worker 与 reviewer 全部确认停止后才集成或清理；超时仅表示等待结束。同一产品一轮只委派一次，即使它同时有变化和未结案审计：两者指向同一次维护活动，拆成两次会重复调查。

固定哪个模型是维护者的选择，本设计不替它补充理由；能被检验的行为只有两条：主会话按项目配置执行，委派一定带显式模型参数，两者都不继承编排协调方的模型。模型变更因此是显式改动，可以在停调度后复核。

### 滚动 PR 活到合并，PR 内每个产品 × 主题一个候选

候选工具使用普通副本裁剪到产品的 catalog 身份及引用、registry、knowledge、current 选择和 audits，不复制依赖、归档或完整工作树。check 复用知识与审计校验；plan 比较产品基线及全局 ID 归属，按产品/主题生成临时合并和完整 before/after。父进程检查 before 后通过内置编辑工具集成，任何 before 变化都重新生成计划，不从旧的共享文件 after 中挑选片段。高影响 reviewer 由父进程安排，避免 worker 占据名额等待另一 worker；不引入固定并行上限或新调度框架。

PR 合并前，后续每日轮次 fetch 远端、切回同一条分支、普通合并 `origin/main` 后继续提交，而不是每天新开一条。候选上限落在这个未合并 PR 的整体上：同一产品 × 主题在 PR 里最多一个 edition／topic，当天的新变化直接修订它，不追加第二个版本，也不顺延、不丢弃——PR 内容始终等于该分支与 `main` 的全部差异。合并保持普通合并：巡检不改写 `main` 历史，不 force push，不 rebase 已推送分支，main 的内容始终等于已合并的巡检 PR 与人工 PR 的普通合并结果。

`delivery=pr` 明确排除本地发布与受管二进制：这两项依赖本机状态，放在无人值守轮次里会让「已发布」与「已合并」出现第二种含义。合并到 `main` 后的对外发布由既有发布 CI 推进，不需要维护者补一步；受管二进制是独立流程，合并也不会触发它。

### 专用 worktree 与主进程持有的 PID 锁

巡检要落本地提交并推分支，共用主工作区会把维护者的未提交改动卷进 PR，因此使用编排工具管理的固定专用 worktree。互斥交给主进程持有的 PID 锁：锁记录 owner PID、`tempRoot` 与报告路径，父进程不自己拼临时目录。不引入守护或 keeper 进程——多一个常驻进程就多一处需要判断它是否还活着的状态。`start` 用已有 SQLite 的事务原子判活与接管死亡 owner，并清理旧临时输出和本项目死亡 owner 的来源工作区。清理失败时保留旧归属记录，正常路径由显式 `finish` 释放运行锁与临时输出。

### 来源读取是项目外的临时 pinned checkout

`sources:workspace open` 在项目之外固定到观察到的精确提交，`close` 读完即关。记录只保存 `git_source_file` 的 commit、file 与 content_sha256：这三项足以在任意机器上重新取得并核对原件，而 checkout 路径既会失效，又把本机目录写进知识真源。既有 `git_checkout` 记录与保留原件继续可读，不做迁移。

catalog 的 Git 快照同理可以只靠精确 revision 固定身份，`archive_path` 变为可选：无论是否保留归档路径，都记录精确 revision 与内容 hash。官方文档没有可替代的固定身份，原件必须保留。

### `not_retained` 是元数据状态，不是校验通过

只留元数据的记录没有可比较的字节。把它们混入「已验证原件」会让来源审计高估可复核性。因此逐条返回 `verified` 或 `not_retained`，并在文档与开发指南中写明后者不等于原件校验通过；应当保留的原件缺失或 hash 不符仍是错误。

### 清理只删本轮自有对象

收尾在 `finish` 时清理本轮登记的来源工作区与验证输出。保留三样东西：官方文档原件按既有策略留在忽略归档，章节文档与来源元数据、审计、报告作为 Git 历史永久保留。源码读取是临时的，记录里只有提交、文件与内容 hash。巡检不接管二进制与完整日志的保留。归属不明、owner PID 不匹配或仍在使用的对象保留并在报告中点名，不用 `rm -rf` 扫目录；巡检每日本身不写入受保护数据，因此不承诺固定峰值占用。

### 启用前保持禁用

命令未合入 `main`、主会话模型或显式子代理模型参数未被原生 subagent 工具实际接受时，调度注册为禁用。启用前手动触发一次验证 PID 锁、只读观察、必要性判断、隔离并行候选、闸门与推送整条链路，不用一次真实调度去试基础设施。

## Risks / Trade-offs

- PR 跨多个产品并可能持续数日，回退以 PR 为单位 → 候选上限落在产品 × 主题，新变化修订已有候选而不是堆叠版本。
- 显式模型不可用时当日无巡检 → 报阻塞并保留在途状态，不静默换模型。
- 临时 checkout 短命，调查的复现依赖记录的 commit 与 hash → 记录字段足够重建，且不再有失效路径需要清理。
- 专用 worktree 与主工作区分叉 → 每轮把 `origin/main` 普通合并进滚动分支，不在本地长期分叉知识真源。
- PR 长期不合并会拉长复核窗口 → 分支保持可读可重建，报告逐轮列出该 PR 当前包含的产品 × 主题。
- PID 锁意味着长轮次会挡住补跑 → 宽限 60 分钟，错过的轮次在窗口内补跑；不并发以免交错写入。

## Migration Plan

1. 合并来源 schema、审计状态与只读观察、工作区与锁命令，并在 `main` 上验证 `sources:check` 不写文件、`sources:audit` 的 `not_retained` 输出正确。
2. 同步 `harness-maintenance` 的 `delivery` 段与 `harness-monitor` Skill，确认 `pr` 轮次不触碰发布指针与受管二进制。
3. 按禁用状态注册每日调度，完成命令可用性与模型两项核对。
4. 手动触发一次巡检，核对 PID 锁、只读观察、必要性判断、隔离并行候选、闸门、在线构建校验、推送与收尾清理，再打开每日调度。
5. 首个真实 PR 合并后，确认既有发布 CI 按 `main` 正常推进，且合并没有触发受管二进制刷新。

回退方式：停用调度即可，不涉及知识版本回滚；已合并 PR 按普通合并处理，需要时用新的修正 PR 前进。
