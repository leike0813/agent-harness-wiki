# Design

## Context

动机见 proposal.md。现有发布组装从不可变归档提取各发布自身的数据树，再搭配候选页面；台账单独记录每个协议的 current、已验证 recovery 与部署意图。只有 v1 有生产构建器。

## Goals / Non-Goals

**Goals:** 用台账预测部署后的两个在线身份，与实际切换复用同一恢复版选择规则；完整归档保持独立、不可变。

**Non-Goals:** 不修改数据协议、消费者选版、Pages 容量预算或归档资产，不引入清理服务。

## Decisions

1. 每个受支持协议仅选择 current 与 recovery。对本次目标协议，current 换成候选；原 current 已验证且不同于候选时成为 recovery，否则保留不同于候选的原 recovery。将这条规则共享给部署组装与切换确认，避免三份数据进入部署或台账指向未部署的恢复版。
2. 移除按退出时间选择 30 天在线历史的逻辑；退出时间继续保留为事实记录。归档不执行任何删除，历史归档可显式选为恢复目标。调高预算不能解决每日累积，因此维持 768 MiB 门禁。
3. 冻结协议继续保留自己的两份数据至至少 90 天公告期结束，退役不再依赖旧发布退出窗口。未知部署仍阻止计划与退役，避免根据未确认状态排除数据。

## Risks / Trade-offs

- 较早固定发布的 MCP 进程可能无法继续取未缓存资源 → 文档明确重启以绑定当前版，归档恢复入口继续可用。
- 恢复到很早的归档后，下一部署仍应只有两份 → 用连续发布、同目标重试、未验证目标和历史恢复验证部署选择与切换结果一致。
- 两份数据及页面仍可能超过预算 → 保留容量拒绝和现站保护，不自动发布或扩大预算。

## Migration Plan

通过独立 PR 合入 main 后，CI 用新选择规则组装候选和已验证恢复数据；在成功部署前现站保持原样。保留所有旧归档和台账，不回写既有归档。上线与巡检启用分别验收。
