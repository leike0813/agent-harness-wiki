# Proposal

## Why

The source boundary now distinguishes a repository commit from a packaged CLI, but production knowledge only identifies an older Codex source checkout and an unversioned page. The next M1 step needs five exact, independently traceable package Targets and honest investigation coverage before any capability fact is published.

## What Changes

- Fix one Linux/x64/glibc npm release for Codex CLI, Claude Code, OpenCode, Pi, and OMP, with official registry identity, package integrity, and a project-owned pnpm package set.
- Record seven topic coverage states and source-linked investigations for every topic on each Target, including concrete evidence gaps where an exact-package conclusion is unavailable.
- Prepare evidence-backed draft Claims for human semantic review; only accepted assessments enter a production fact release.
- Keep only the current selected executable package set locally, while preserving release metadata and reviewed evidence excerpts for historical queries. Retired package originals are reported as unavailable by explicit audit.
- Align PRD, roadmap, engineering guidance, and contributor documentation with that retention rule.

## Capabilities

### New Capabilities

- `five-harness-investigation`: The fixed five-Target catalog and its source-linked coverage and review gate.

### Modified Capabilities

- `source-provenance`: Add exact npm package provenance and scoped local package retention.
- `knowledge-records`: Add versioned package snapshot identity and source references on investigations.
- `dataset-validation`: Validate package relationships and investigation references offline.

## Impact

Domain schema, dataset validation, offline source audit, production records, OpenSpec specs, documentation, and an isolated pnpm lockfile change. Query and MCP operation names remain the same; the later managed-startup change owns execution of the packages.
