## Earlier draft

> 此前讨论记录，因配置文件示例及其他成稿场景尚未讨论充分，本票已重新打开；以下不是最终决定。

主题页以读者需要查找或使用的机制组织正文。一个能独立解释、配置或排查的机制成为带稳定 ID 的可检索小节；字段、步骤和示例留在所属节内，必要时用三级标题或表格。不要把 53 个调查问题机械排成 53 个小节。

每节采用[已确认的短样](../chapter-writing-prototype.md)所示的解释深度：让读者知道机制是什么、配置放在哪里、怎样生效，以及哪些条件会改变结果；涉及配置入口时给有来源的最小示例。正文用自然标题和连贯段落，避免以 `skills.format` 这类编号起句或仅堆字段名称。第一方字段、事件与选项仍须调查完整；项目已有的[调查与成稿契约](../topic-contract.md)规定其范围。数量较多时，先解释共同机制，再用表格逐项写明用途、默认值和生效条件。来源不足以给可靠语法时明确记录缺口。

调查问题编号保留在结构化问题索引中，并能定位对应小节；站点成稿应让读者找到该映射，但编号不打断正文。页首简述固定来源与版本边界，段落或表格行就近引用；冲突、未验证和不适用项只在受影响的地方说明，避免每节重复整段范围提示。

验收时按读者任务抽查，而非按字数：能否从主题目录找到机制、按示例理解配置入口与生效条件、从引用核对关键结论，并通过问题索引找到既定问题的答案。对不适用或尚未查明的问题，能否清楚看到依据或缺口。该标准指导后续章节修订；本票不修改已发布的知识正文或查询实现。

## Answer

主题页沿用[前两轮已确认的正文与分节方向](../chapter-writing-prototype.md)：以读者能独立查找和使用的机制划分带稳定 ID 的小节，正文按自然阅读顺序解释机制、操作、处理链和适用条件；调查问题编号留在可定位小节的索引中。完整调查第一方字段、事件和选项，用正文说明共同机制，必要时用表格逐项列明用途、默认值与生效条件。页首简述来源范围，引用和局部缺口贴近相应结论。

凡涉及读者需要创建或修改的配置文件，正文必须写出准确的文件路径与适用作用域，展示有固定来源支撑、可放入该文件的最小完整配置块，并解释示例中的字段、前提、生效结果和可观察的检查方式。不同语法或处理链分别示例；例如同在 `config.toml` 中，stdio 与 HTTP MCP server 应各有一例。示例不必堆满所有可选字段，但字段清单仍须完整。凭据只用清楚标记的占位值，不写真实 token。

其他需要实例的情形按读者动作选择呈现形式：目录和文件结构给目录树及必需内容；CLI 操作给命令、前提与可观察结果；Hook 等回调给最小输入输出及其对宿主操作的作用；优先级或冲突规则给两份相互竞争的输入与最终生效结果。这些实例应解释“为何得到这个结果”，不能只给代码块或命令行。若某机制不适用，或固定来源不足以确定可靠语法、输出或结果，应写明依据与缺口，不制造示例；示例的来源、平台与软件版本边界就近标注。

内容验收按适用机制检查：读者能否找到入口、看懂并使用示例、分辨生效前提、观察结果、追到来源，同时能由问题索引找到既定问题。不得仅以问题状态为 `answered`、字段清单齐全或章节页存在，就认定正文可用；也不以字数和示例数量作机械指标。本票只确定成稿标准，知识正文和查询实现另行修订。
