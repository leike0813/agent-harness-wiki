# 定义上游变化到新知识发布的细则

Type: grilling
Status: resolved
Assignee: codex
Parent: [重新确定知识库交付与维护契约](../map.md)

## Question

手动发起更新后，如何分别追踪源码提交、官方文档快照和二进制版本，判断受影响的小节、处理源码与文档冲突、选择另一 Agent 复核、留下可读审计记录，并在无需人审的前提下决定何时构建或保留旧发布？

## Discussion

- 用户确认：日常更新检查并记录软件包版本与来源身份，但新包出现本身不证明知识变化；取得、替换和启动受管二进制归“定义最新二进制与隔离环境的维护方式”议题。
- 用户确认：普通更新由调查 Agent 自检；来源冲突、推翻已发布配置步骤或涉及多个主题的关键加载机制时，请另一 Agent 独立复核。
- 用户确认：每次手动检查留结构化审计 YAML；有实质变化、来源失败或未解决分歧时另写简短 Markdown，说明变化、知识影响和处理结果；完全无变化时只留 YAML。
- 用户确认：按固定来源定位受影响的调查问题、小节与跨主题引用，无法划清影响或共用加载入口变化时扩大调查并记录理由。
- 用户确认：源码与文档分歧先检查版本和条件，再请另一 Agent 复核；无法消除时并列来源与分歧，不给单一配置结论。复核尚未完成的受影响问题暂缓更新。
- 用户确认：上游变化没有改变读者可见的章节、来源定位或版本映射时只结案审计；可验证更新通过校验后自动构建新发布。其他章节或产品受阻时可发布已完成部分，受阻章节保留原来源范围和待处理审计。

## Resolution comment

由用户手动发起一次更新，可以选择一个或多个 Harness。每个 Harness 分别观察官方源码 HEAD 的 commit、登记官方文档的固定内容快照，以及软件包的版本和来源身份；三种身份和失败状态分别入审计。新软件包版本只是一条版本线索，不证明章节改变，也不自动绑定源码提交或触发知识发布。二进制取得、替换和最小启动检查归“定义最新二进制与隔离环境的维护方式”处理。失败来源不抹去此前成功观察，也不阻断其他来源的检查。

调查 Agent 比较固定来源，把变化追到调查问题编号、写作小节、来源引用和跨主题链接。配置入口、共用加载器或难以界定的差异须扩大范围，审计中写明查过什么、为什么认为其余章节不受影响。仅改变日志等与知识内容无关的差异可以审计结案；旧章节仍指向原固定来源，不冒充已调查新提交。新版本出现也不把旧章节外推为新包事实。

普通更新由调查 Agent 引用固定来源、自检并直接采纳。来源冲突、推翻已发布的配置步骤，或涉及多个主题的关键加载机制时，请另一 Agent 独立复核。先检查冲突是否来自版本、分发或生效条件；仍未消除时，在受影响问题中并列说法、各自来源及边界，不给单一配置建议。独立复核尚未完成时，该问题保持待处理；其他已查明内容可以继续发布。

每次检查留结构化审计 YAML；有实质变化、来源失败或未解决分歧时另留简短 Markdown，写变化意义、知识影响、结论及尚待处理的范围。只有审计变化而没有读者可见的章节、来源定位或版本映射变化时不建新知识发布。有可验证改动时，校验问题索引、来源定位、版本与适用边界、站点和 MCP 共用内容及发布完整性，随后原子构建并切换本地发布，不设人审门禁。受阻章节保留旧来源范围与待处理审计；已完成的其他章节或 Harness 可进入新发布。失败不改当前发布，旧发布与历史章节保持可查；运行中的 MCP 进程重启后才读取新发布。

现有[项目调查 Skill](../../../.agents/skills/harness-investigation/SKILL.md)和 PRD 仍要求人工语义复核，Skill 还禁止接受事实与切换发布；这些旧规则由[“确定现有实现迁移与 OpenSpec 修订边界”](09-migration-handoff.md)安排替换。
