# 定义最新二进制与隔离环境的维护方式

Type: grilling
Status: resolved
Assignee: codex
Parent: [重新确定知识库交付与维护契约](../map.md)

## Question

每个产品“最新版本”的渠道与更新时间怎样确定？怎样下载、校验、替换 Git 忽略的旧制品，保存运行入口与隔离配置，并完成不使用真实凭据或付费服务的最小启动检查？无法启动时怎样记录而不阻断知识发布？

## Discussion

- 用户确认：现有五个 npm 产品以登记官方包的 `latest` dist-tag 为候选渠道，记录解析出的精确版本和 integrity；不根据版本号猜最大值，其他官方渠道需要单独登记。
- 用户确认：用户手动发起更新且发现新版本时，同一次流程尝试刷新受管包；知识调查与发布不等待刷新成功。
- 用户确认：新版本无法启动时保留上一个可启动受管环境，新版本作为待处理候选记录失败；启动成功后才切换并清理旧包。
- 用户确认：当前 Linux 环境用 `bwrap` 做最小启动检查，隔离临时配置根和工作目录，不注入真实凭据，默认断网、限制时间和输出；沙箱不可用时记录阻塞，不自动退回只替换 `HOME` 的弱隔离。
- 用户确认：继续禁用安装脚本；对于 Claude Code、OpenCode 等主命令是占位脚本的包，直接定位锁定的平台专用依赖中的可执行文件。缺失依赖时记录阻塞，不临时运行 postinstall 或另行下载。
- 用户确认：每个产品保存明确运行入口、运行方式和沙箱配置；在沙箱中执行适用的离线 `--version` 或 `--help`，检查退出状态和身份输出。审计记录结果及失败原因，不把启动检查当作主题能力证据。
- 用户确认：`latest` 标签退回较旧版本，或同一版本的 integrity 变化时，记录异常并暂停自动切换；知识发布不受影响。

## Resolution comment

对当前五个 npm 产品，以各自登记官方包的 `latest` dist-tag 作为候选渠道；观察到的精确版本、registry integrity、渠道与检查时间分别入审计，不按 SemVer 最大值猜“最新”。其他官方分发渠道接入时逐个登记，不把源码 HEAD、文档快照与包版本视为同一身份。用户手动发起更新且渠道指向新版本时，同一流程尝试刷新受管环境；知识调查与发布独立完成。

候选先在 Git 忽略的隔离位置取得并精确锁定，用包管理器锁文件及 registry integrity 核验主包和需运行的平台依赖，安装时禁用生命周期脚本。明确记录运行入口和所需运行时；Claude Code 与 OpenCode 当前包的主命令在禁用 postinstall 后是占位脚本，须从已锁定的平台专用依赖直接定位可执行文件。平台依赖缺失、身份校验不符或必须额外下载时保留阻塞，不临时放行脚本。现有 `research/package-set/` 的精确版本清单与锁文件仍是当前受管包身份的事实源；候选失败时不覆盖当前可用包集。具体 staging 与切换文件布局由迁移议题决定。

当前 Linux 的最小启动检查使用 `bwrap`：按明确路径运行候选，制品只读，临时配置根和工作目录，环境中不带真实用户凭据，默认断网，并限制时间、输出及进程资源。每个产品用已登记的离线 `--version` 或 `--help` 等命令检查能否启动、正常退出且输出可识别的产品身份；把实际命令、运行时、沙箱配置、结果与失败原因留在受管配置和审计中。它只证明该精确制品在该隔离条件下可启动，不证明任何主题能力，也不代表其他平台通过。沙箱不可用时标记阻塞，不自动降为仅替换 `HOME` 的运行方式。

候选通过身份校验和最小启动检查后才切换为当前受管版本，再清理旧包字节；失败时保留上一个可启动版本和待处理候选记录。若 `latest` 指向更旧的可比版本、同版本 integrity 变化或版本不可安全比较，暂停自动切换并记录异常，待查明后再处理。受管环境状态与知识发布状态分开；候选或沙箱失败均不阻断已验证的知识更新。现有扫描器下载新 npm tarball、包集原地固定版本及调查 Skill 不负责运行的做法，由[“确定现有实现迁移与 OpenSpec 修订边界”](09-migration-handoff.md)统一安排迁移。
