## Question

哪些仓库事件触发公开知识和文档站的自动发布，使用什么输入及知识发布身份？自动流程如何从干净 checkout 产生已验证的词法数据和读者页面，保证机器数据与页面对应，并在校验、构建或部署失败时保留先前可用版本？

明确并发发布次序、当前指针与不可变资源的关系、旧 MCP 进程读取的资源保留期限，以及发布损坏时怎样恢复。知识变更是否触发 npm 程序发版另行明确，不能把两个版本体系混为一个。

## Inputs

- [缓存与失败决议](03-online-failure-and-cache.md)：默认客户端必须在线确认当前发布，坏发布不自动回退；旧进程仍绑定旧发布。流程需明确其资源保留期限和恢复行为。
- 来源存在性目录与全部登记来源文件属于完整发布，必须同步上线；缓存只帮助已读资源复用，不能替代发布完整性或保证旧资源均已缓存。

## Answer

### 触发与构建边界

`main`每次push自动验证、构建并发布；PR只验证，保留手动重跑入口。普通知识更新不触发npm程序发版，知识归档也不作为npm发版事件。

新发布的知识输入来自干净checkout的catalog、registry、结构化知识、固定问题和锁定构建工具。完整校验真源后，选择在线保留范围，再生成词法索引、目录、主题导航、章节、来源及读者页面；投影后再次核对全部引用和资源关系。数据与页面由同一份知识生成，共用在线发布身份、一起部署。

构建不依赖维护者本地`releases/`、来源原件或语义模型，不访问上游补知识，不执行上游harness。旧在线资源由已保存归档取回，用于履行保留承诺，不作为新知识真源。缺少必需归档时发布失败，不能临时重建不同内容并沿用其身份。发布版MCP检索能力按[检索能力决议](05-optional-semantic-search.md)执行。

完整在线发布必须含来源存在性目录、全部收录章节的来源、catalog身份来源及相应导航、映射和词法块。裁剪标记表达资源不在线，不得作为普通章节入口指向缺失文件。正文、目录和搜索必须一致；不通过HTML反向提取事实。

### 发布身份与不可变资源

首版在线`release_id`使用`web-v1-<完整Git提交SHA>`；协议主版本、npm程序版本、在线发布、本地全历史发布、章节版本及被调查软件版本分别表达各自身份。在线投影不能沿用内容不同的本地全历史发布身份。

首次生成在线发布时固定`knowledge_published_at`并随成功产物保存。同一提交同一协议分区重跑复用已保存成功产物；同名不可变资源不得原地改写。构建修正通过新提交产生新身份，不能用当前时间在重跑中偷偷变更已有清单。固定输入及固定参数仍要求可重复构建。

`current.json`是可变指针，发布内的数据是不可变资源。每次Pages部署目录包含完整候选数据、对应页面、候选指针和仍须保留的旧数据，一并验证及部署。页面标识其知识发布；不能分别部署页面与机器数据而声称已经一致。

GitHub官方提供artifact构建、上传及部署链：[自定义Pages工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)、[deploy-pages](https://github.com/actions/deploy-pages)。同次部署及客户端身份校验不构成对所有CDN节点同时切换的承诺；暂时读取失败仍按既定失败与重试规则处理，不能混用发布。

### 本地历史、在线章节与旧发布

| 对象 | 保留承诺 |
| --- | --- |
| 本地结构化知识及本地全历史发布 | 保存完整章节历史，供读取本地发布的MCP查询；不能把Git提交历史直接声称为已构建可查的数据。 |
| 当前在线发布内的章节 | 每个产品×主题保留当前章节及最近一个历史章节版本，带各自完整来源和软件版本映射；不足两版时保留实际存在的版本。 |
| 旧完整在线发布 | 退出current后至少保留30天；在仍受支持的协议分区内，始终保留current及最近一个已验证可用发布。 |
| 在线文档站 | 展示当前在线发布所收录的章节历史；不要求为每份旧完整发布同时托管一套旧站点。旧版页面保存在恢复归档中。 |

章节版本数量不等于软件版本数量，一个章节可对应多个软件版本。npm的MCP进程在本机运行，但仍是在线数据消费者；显式离线缓存也不承诺完整历史。

旧发布资源保留期从实际退出current计算，不从创建时间或归档时间计算。回退后再次成为current的发布继续受保护，再退出时重新按退出时间计算；失败、重跑或创建归档不能冒充一次成功切换。记录实际部署与回读状态，区分已构建、已部署和已验证可用。

章节裁剪与整份旧发布清理独立：新发布可以只收录最近两版章节，仍须原样托管30天窗口内旧发布包含的全部资源。旧进程可以读其缓存，但缓存不能替代服务端保留责任。超期清理后，缺必要资源的旧进程明确失败，需要重启；不能在调用中换发布。

### 有限历史的查询表达

主题索引保留判断已裁剪章节所需的轻量版本、界面、章节及映射范围标记，不带已裁剪正文或完整来源。标记由完整真源投影，不是一套手写版本表，不能被当成可读章节资源。

按既有选版规则应选择已裁剪章节时，`get_topic`或比较中的相应目标返回正常业务结果`history_not_available`，保留请求目标和选版信息，提示通过本地完整发布查询。不静默改选另一章，不把裁剪翻译为unsupported、unknown或从未调查；比较仍保留各目标自己的结果。

其他版本继续按既有精确、前缀、近似及source_only规则解析，且注明在线历史范围有限。裁剪标记不为从未建立映射的软件版本制造历史命中，也不增加edition_id查询参数。来源存在性目录只登记本发布实际收录的来源，保持正常not_found与已声明文件缺失技术错误的区分。

轻量标记也计入容量预算，其增长不能被排除在体积检查之外。数据契约与公共结果DTO须在后续规格中正式加入这些表达，不能用HTTP404推断章节已裁剪。

### 容量、归档与清理

首版全部Pages部署文件的实际字节总量上限为512 MiB，包含页面、静态资源、全部协议分区、所有保留发布和裁剪标记。计算解包后的实际文件大小，不以gzip下载体积或新发布单独大小代替。

超过预算时停止部署，报告实际体积及主要占用，保留原站点。不自动缩短30天／90天承诺、不偷偷删除所收录章节或来源。容量规则是部署边界，不能保证自动更新永远不会受阻。平台当前站点上限为1 GB：[GitHub Pages限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)。

以独立命名的GitHub Release附件保存每份已验证在线发布的机器数据和对应页面。归档至少覆盖仍须保留的旧数据、current与恢复候选；后续CI从归档组装完整Pages目录。消费者只访问Pages，Release附件不是查询时备用数据入口。归档属于知识分发，不进入主分支的知识真源，也不携带原件、模型或本地凭据。

Actions artifact与cache不能作为唯一副本；artifact会按配置到期删除：[官方保留说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)。GitHub Release可附构建资源：[官方Release说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。本决议不承诺站外归档无限保留，清理须保护约定范围及恢复所需资源。

### 并发、失败与恢复

生产发布流水线串行。候选开始部署前确认仍是main最新提交，过期候选跳过；允许跳过中间提交。已开始的部署正常完成，随后处理新候选。旧任务不得覆盖已经上线的较新发布。不能单凭Actions并发组就声称按提交顺序部署：[官方并发说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。

校验、归档取回、构建、容量检查或上传失败时不进入部署，保留现站。部署失败或状态不确定时明确报告并检查实际状态，不能把开始部署当成发布成功。无先前可用站点的首次发布失败则报告未上线。

部署后有界回读current、必要导航及代表性章节、词法查询、来源和读者页面，确认预期发布身份与可读性；完整一致性仍由部署前整库验证负责。回读成功才记为已验证可用。失败标红，提供手动恢复最近可用发布入口，不因一次网络故障自动回滚。

恢复使用已保存页面与指针目标，重新组装并保留当前承诺范围内的旧数据，包括已被进程绑定的故障发布。恢复不改写不可变数据，也不把故障发布记为可用；同样经过串行、容量及完整性检查和上线回读。手动恢复是明确选定旧目标的操作，不受普通自动候选必须为main最新提交的规则限制。恢复失败须如实报告，不能保证平台故障时仍能恢复。

客户端仍不自动回退：新进程解析恢复后的current；旧进程继续绑定自己的发布。恢复页面及指针不能修好已经绑定损坏数据的旧进程，它需要重启。

### 数据协议退役

首版只实现data/v1。将来新协议主版本上线时，旧分区冻结在最后可用发布、公告明确退役日期，至少再保留90天。到期前旧分区的current、导航及所需资源仍可读；旧发布30天窗口及恢复保护同时适用。

到公告日期且保留义务满足后，才能清理旧分区数据，旧入口留下机器可读退役提示要求升级客户端，不伪装成空知识。旧客户端不自动跨协议读取；缺缓存的旧进程不能借退役提示改绑新协议。退役标记的schema与客户端初始化错误DTO由交接规格落实。

新旧分区共同计入512 MiB预算，容量不足阻止部署，不提前退役。协议退役是明确结束该分区支持的动作，届时解除其current与恢复版本的长期保护；本地完整历史不随在线退役删除。
