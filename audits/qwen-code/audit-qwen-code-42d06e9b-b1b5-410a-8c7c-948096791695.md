### `packages/core/src/core/coreToolScheduler.ts`

新增 `modToolCheck` 门控，位于权限流计算之后、确认详情改写之前：

- 调度器把 `{tool, input, tool_use_id}`（`input` 为 `structuredClone(toolParams)`）交给 `modToolCheck`，并把当前 `finalPermission`（`default` 归一为 `ask`）作为入参 `decision` 一并给出；
- 结果按**限制性方向**合并：原权限不是 `deny` 时，Mod 的 `deny` 置为 deny 并附理由（缺理由用 “Tool \"…\" is denied by a Mod.”），Mod 的 `ask` 仅在原权限为 `allow` 时降级为 `ask`；返回值不在 `allow`/`ask`/`deny` 内直接抛错；
- `getOrCreateNestedToolScheduler` 显式传 `modToolCheck: undefined`，即**嵌套的 code-mode 调度器**不继承该中间件；
- **subagent 是另一条路径**：subagent 运行时自行构造 `CoreToolScheduler`（`packages/core/src/agents/runtime/agent-core.ts:2345`），而全树中唯一把 `modToolCheck` 传给 `CoreToolScheduler` 的构造点是 `nonInteractiveToolExecutor`（`:76-78`），因此 subagent 同样不会带上该选项——但这是"不经过唯一产生点"，不是"显式置 undefined"。

影响判定：

- **`native_plugins` 需维护**——本章 `plugins-api` 原文断言“扩展通过目录或清单字段贡献组件，而非通过运行时 API”。这是已发布表述，而 `modToolCheck` 是运行时的真实工具权限门控，因此新 edition 中保留原断言但标注适用边界并补写 Mod 例外，不删除原文。
- **`custom_agents` 不需维护**——中间件不向嵌套调度器继承（显式置 `undefined`），subagent 调度器则因不经过唯一产生点而不带该选项，两条路径各自有独立证据；本章关于“父会话宽松模式优先”的表述未被推翻。
- **`mcp` 不需维护**——`withPreToolUseAskReason`、`planModeDetails`、`isNonInteractiveDeny` 三条既有引用所指的代码路径本轮未被触及；新增块在其之前且仅在 `modToolCheck` 存在时执行，`mcp-v4` 的三条引用仍成立。
