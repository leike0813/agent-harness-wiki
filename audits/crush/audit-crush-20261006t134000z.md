## 语义 triage

`init.go` 的唯一生产改动在 `pingSession`：

```go
err := s.Ping(pingCtx, nil)
// MethodNotFound means the server answered; it just doesn't implement ping.
var wireErr *jsonrpc.Error
if errors.As(err, &wireErr) && wireErr.Code == jsonrpc.CodeMethodNotFound {
    return nil
}
return err
```

判定的是“这个 server 能不能用”，而不是“ping 有没有报错”。服务端回 JSON-RPC
`MethodNotFound` 说明它应答了、只是没实现 `ping`，按探测通过处理；其它错误（连接断开、会话已关闭、
探测超时）仍然照旧返回。这与 `resources.go` 里 `isMethodNotFoundError` 对 resources 列表的静默降级是同一种取舍。

沿调用关系核对的结果：`pingSession` 只有 `getOrRenewClient` 一个生产调用方（`init.go:779` 快路径、
`init.go:806` 锁内复查）。快路径“探测通过就直接返回现成会话”意味着不实现 ping 的 server 不再每次取工具
都被拆除重建；锁内复查同样如此。超时、会话重连、代次作废等其余调用方行为本轮没有变化，因此只写 ping 语义，
不扩到重连策略。

`channel` 机制（`channel_enabled`、`--channels`、`SubscribeChannelEvents`、`EventChannelMessage`）此前已在
章节登记，本轮不是首次引入，未重复采写。

`mcp.capabilities` 逐题核对：tools / resources / prompts 三条路径本轮未被触及，答案与正文都不需要改。
`configuration` 的隐藏旗标 `--channels` 位于 `crush-cli-configuration-v1` 第 140 行，证据是
`ref-crush-code-cli-flags`（`internal/cmd` 下的旗标注册），本轮未变更，不受影响。
