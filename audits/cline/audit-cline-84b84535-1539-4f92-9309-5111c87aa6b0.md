## 已验证的机制

`discoverRulesLikeFiles` 从

```ts
entries.filter((entry) => entry.isFile() && isMarkdownFile(entry.name))
```

改为逐项判断：`entry.isFile()`，**或** `entry.isSymbolicLink()` 且 `stat(filePath)` 目标是普通文件（`stat` 失败按 `false` 处理）。因此 rules/workflows 搜索目录里指向普通文件的符号链接成为候选，路径、`fileName` 与覆盖 id 都取链接自身的名字和位置；指向目录、断链、自环的链接被跳过。`unified-config-file-watcher.ts` 的通用目录扫描改成同一条规则。

运行时核对（在 pinned workspace 用 `bun` 直接加载该提交源码执行，非静态推断）：

1. 同一脚本分别在 baseline 与 observed 源码上运行，构造 `configs/{regular.md, linked.md→../external/source.md, broken.md→不存在, directory.md→目录, circular.md→自环, ignored.json→markdown 内容的 .json 链接}`。
   - baseline：`rule` 快照 1 条，仅 `regular.md`。
   - observed：`rule` 快照 2 条，`linked.md` 读到 `"Follow linked instructions."`，断链/目录/自环/非 markdown 链接均未进入快照。
   - 上游新增用例 `user-instruction-config-loader.test.ts` 对 rule 与 workflow 两条通道断言同样的 2 条记录。
2. 重载触发：`start()` 后订阅事件，只写链接目标文件时 **0 个事件**且快照仍是旧内容；写链接所在目录的另一个文件时才产生 `upsert` 并读到目标的新内容。与 `sdk/DOC.md` 的表述一致：`fs.watch` 只挂链接所在目录，目标文件的改动要到下一次 `refreshType` 或新会话才生效。
3. 对照通道：skill 侧 `discoverSkillFiles` 的文件分支仍是 `entry.isFile() && entry.name === SKILL_FILE_NAME`，未跟进链接判定。实跑确认指向目录的链接被发现，而搜索根下直接放一个指向别处文件的 `SKILL.md` 符号链接**不**被发现。

- **cron（`cron-runner.ts`、`sqlite-cron-store.ts`）**：改动为取消被更新排期取代的 queued 运行、把 `finishReason === "error"` 当作失败上报、报告补 `usage`/`toolCalls`、`claimDueRuns` 由具名参数改为位置参数（注释说明 `bun:sqlite` 会把未加前缀的具名参数绑成 NULL 从而静默匹配不到行）。本产品章节没有任何一处陈述 cron 的路径、优先级、加载顺序或诊断入口；`configuration` 章节只在目录树里列出 `.cline/cron/` 这一目录名，而该路径常量本轮无 diff。八类固定问题也不覆盖定时执行，故不新造主题或结论。

- **UI 与 VS Code 路径**：`cloud-onboarding.tsx`、`routine-view.tsx`、`agent-conversation-layout.tsx` 为示例桌面端与共享 UI 的样式/目录刷新时序；`apps/vscode/src/utils/fs.ts` 虽同样改为跟随指向普通文件的符号链接，但属于 VS Code 扩展的 `readDirectory`，与 cli 的指令文件加载不是同一条路径，而本产品章节只发布 cli 界面的答案。
