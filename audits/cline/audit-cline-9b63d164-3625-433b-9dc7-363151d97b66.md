# Cline 上游审阅报告 · 2026-10-03

## 给维护者的结论

Cline 仓库从 `3435f72f` 前进到 `39ff2359`（`apps/cli` 包版本 3.0.66 → 3.0.68）。这一段不是小修：自定义 provider 的可用性、模型目录的发现与记账、MCP 工具输出的超限处理、团队状态的持久化方式都换了实现。

其中最值得注意的一条是**自定义 provider 之前在 CLI 里选了却用不了**。provider 与模型选择器会列出 `providers.json`/`models.json` 里登记的条目，但 agent model 那条路径没有把目录里的 provider 桥接进网关，跑任务时报 `Unknown or disabled provider`。本次提交补上了桥接，变更日志也把它列为用户可见修复。已发布章节此前把「网关把会话请求路由到对应协议实现」写得过于笼统，没有说清自定义 provider 需要显式登记，新版按代码写明。

模型目录一侧的变化围绕**归属与凭据边界**：条目新增一个可选字段，把「来源发现的模型」与「用户手工加的模型」分开记账，刷新因此可以剪掉来源不再列出的模型而保住手工项；相应地，模型条目不再复制 provider 能力，改为登记时继承。取目录时可以带凭据，但只发给与 provider `baseUrl` 同源的地址，并禁止带凭据的重定向。

MCP 工具现在统一带 `resultPolicy: "cache-oversized"`：输出超过阈值时完整结果进会话内存缓存，模型拿到预览加一个 `cline://cache/...` URI，用 `read_files` 分页读回。这是新增的机制，不是配置项。

**本轮确实推翻了已发布内容，因此触发独立复核。** 六个官方文档来源全部 hash 变化，但既有引用短摘录逐条核对后仍与新原件一致；真正的推翻来自仓库提交本身——已发布的 `custom_providers-v1`（自定义 provider 跑任务会以 `Unknown or disabled provider` 失败）与 `custom_agents-v3`（团队状态记在 `teams/{team-name}/`）都被本轮结论取代。`configuration`、`skills`、`hooks`、`native_plugins` 四个主题的机制文件本轮未进入 changed_paths，保留原章节版本。

## 变化的意义与证据边界

### 自定义 provider 现在能在任务里真正跑起来（custom_providers）

影响 `providers.protocol`、`providers.entry`。`createAgentModelFromConfig` 建好网关后调用同步版的目录 provider 解析函数并注册结果；该解析函数对网关已知的内置 id 和目录里不存在的 id 返回 `undefined`，由网关自己报错。证据能证明「桥接存在」与「哪些 id 会返回 undefined」，但不能证明任何具体 provider 在某个已发布版本里的构建行为——本章仍按来源级知识记录（`version_applicability: unknown`）。

### 模型目录的归属记账与同源凭据（custom_providers）

影响 `providers.models`、`providers.metadata`、`providers.auth`、`providers.diagnostics`。新增的归属字段是 `StoredProviderEntrySchema` 的可选键，schema 为 `.passthrough()`，因此旧条目仍可解析。凭据转发规则可证：origin 不同则不发；baseUrl 非法时按「无法建立信任」处理但不阻断无凭据加载；一旦附加任何头即禁止重定向。

两处新的失败类型已分别记录：目录发现失败，以及发现成功但来源为空（后者的消息与显式清空模型列表的校验错误同文）。凭据保存路径吞掉发现失败，所以「密钥保存成功但模型列表没变」是预期行为。仍未解决的是：这两个错误在 CLI 上分别呈现为什么样的用户可见文案，本轮没有固定来源可证。

### MCP 工具输出的超限回收（mcp）

影响 `mcp.capabilities`、`mcp.exposure`。缓存是会话私有、纯内存，上限 16 MiB，闲置 5 个迭代回收，URI 查阅不延长寿命。触发阈值 `maxToolResultChars` 默认 8000，可用 `CLINE_MESSAGE_BUILDER_MAX_TOOL_RESULT_CHARS` 调整。`mcp.json` 不需要任何配置。

### 团队状态改为增量批处理（custom_agents）

影响 `agents.limits`。`TeamStore` 新增 `persistBatch`（单个事务应用事件 + 实体增量），整份重写的 `persistRuntime` 保留给运行时之外的使用者；批对象里的整份状态访问器明确只给文件回退存储用。变更日志称既有数据在第一次被打开时自动压实。

**本轮修正了上一版的一处路径错误。** 变更日志与代码都把团队库指向数据目录下的 `db/teams.db`（经 `resolveDbDataDir()`），而上一版章节把团队状态记在 `teams/{team-name}/`——那是文件回退存储的路径。`createLocalTeamStore` 先试 SQLite、失败才回退文件，两套路径与各自可用的环境变量已在 v4 中并列写明。

**但这只是代码一侧，文档在同一提交里仍未跟进。** `docs/cli/agent-teams.mdx` 的「Team State」一节在 39ff2359 仍写 `~/.cline/data/teams/[team-name]/`，既不提 SQLite，也没有给出「先试库、失败才回退」这层选择，只列了任务板、inter-agent 信箱与任务日志三样内容。v4 现在把两种说法并列，并写清各自边界：文档描述的正是文件回退那一套的目录形态，真正写到哪里取决于建库是否成功；判断状态在哪，应先看 `CLINE_DB_DATA_DIR` 与 `CLINE_TEAM_DATA_DIR` 指向，而不是只按文档路径去找。
