## 变化的意义与证据边界

### stdio 的 initialize 预算：3 秒 → 10 秒

`DEFAULT_MCP_CONNECT_TIMEOUT_MS` 由 `3_000` 提升到 `10_000`。源码注释自己写明理由：这 10 秒覆盖 marketplace server 真正使用的启动器——Windows 上经 `cmd.exe` 起的 `npx`/`uvx` 即使热缓存也要 3-6 秒才到 initialize，3 秒预算会把每一台这样的 server 静默丢出会话；`connect()` 最多花两次预算（先试换行分帧再试 Content-Length），最坏约 20 秒，仍在 hub 的 30 秒上限之内。比这更慢的（JVM 起的 Oracle SQLcl、首次下载包）仍需显式 `timeout`。死命令照旧由 spawn error/exit 路径快速失败，只有「活着但不说话」的 server 会等满预算。

边界：`DEFAULT_HTTP_MCP_CONNECT_TIMEOUT_MS` 本来就是 `10_000`，所以远程连接预算没变；变的只是 stdio 这一侧。**这是源码树上的行为，没有绑定任何 npm 版本**——npm 侧只观察到 3.0.68→3.0.70 的身份变化，不据此写任何版本映射。

证据 `ref-cline-mcp-connect-budget-10s` 固定到 `95e54e4a` 的 `client.ts` 50-61 行，新建 snapshot/artifact 记录该文件的 `content_sha256`。

### 新增的 stdin 写失败路径

server 在请求写到一半时死掉或关掉 stdin，那次写在 stdin 流上异步失败；此前没有监听器，Node 会把它当作宿主进程上的未捕获异常。现在 `StdioMcpClient`：

1. 给 `child.stdin` 挂 `error` 监听，第一次失败把消息记进 `stdinFailure`（`??=`，只记第一次），并起一个 `STDIO_MCP_GRACEFUL_SHUTDOWN_TIMEOUT_MS`（250 毫秒）的定时器，`unref` 所以不挡事件循环；已有定时器时不重复起；
2. 正在退出的 server 有这 250 毫秒自己走完，届时由既有的 `exit` 处理器报它自己的退出码与 stderr；
3. 250 毫秒后仍在跑的，定时器让所有 pending 请求以 `MCP server "<名字>" stopped reading its input before the request was fully delivered (…) and did not exit.` 失败，并走与 `disconnect()` 相同的 SIGTERM→SIGKILL 升级关掉它；
4. 标记会拼进错误文本：超时错误与进程退出错误都追加 `The server stopped reading its input before the request was fully delivered (…).`。所以这两类错误里出现这句，根因就是 server 提前停止读取，而不是纯粹的预算超时——这是本轮新增的、读者能用上的诊断区分；
5. `disconnect()` 与重新 spawn 都调 `clearStdinFailureTimer()`，spawn 还把 `stdinFailure` 重置为 `undefined`，标记不会跨进程残留。

证据 `ref-cline-mcp-stdin-failure`（462-472）、`ref-cline-mcp-stdin-failure-timer`（474-487）、`ref-cline-mcp-stdin-failure-message`（629-648），全部固定到 `95e54e4a` 的同一文件。

### custom_providers：核对后不改写

`{#providers-auth}` 已发布的三条结论逐条核对：

- **「`apiKeyEnv` 白名单回退」**：`apiKeyEnv` 字段本身没变，`cline`/`openai`/`deepseek` 的环境变量名照旧。仍成立。
- **「凭据落点是设置文件的 `apiKey` 或 `auth.accessToken`/`refreshToken`，没有系统钥匙串」**：写入路径没变。仍成立。
- **「没有凭据预检，后端返回的 401 才是权威信号」**：`apiKeyOptional` 的注释明确写的是「宿主不得在开始会话前索要 key，端点自己的认证错误才是权威」，方向一致。仍成立。

新增的部分是：`ProviderAuthInfo` 多一个 `apiKeyOptional?: boolean`，`resolveProviderApiKeyOptional(provider)` 只读 `provider.metadata.apiKeyOptional === true`；`builtins.ts` 给 Ollama、LM Studio、LiteLLM、openai-compatible 本地端点、Vertex（ADC）、Bedrock（profile/默认凭据链）打上该标志；`local-provider-registry.ts` 用常量 `CUSTOM_ENDPOINT_METADATA = { apiKeyOptional: true }` 给用户自建与设置文件登记的 OpenAI 兼容端点统一带上；`local-provider-service.ts` 在列出 provider 时按标志决定 `auth` 块里带不带 `apiKeyOptional`。`apps/cli/src/tui/utils/provider-configured.ts` 则让 TUI 的 `isProviderConfigured` 把环境变量里的 key 当作已保存的 key 去跑 `isProviderSettingsUsable`；新增的 `getProviderApiKeyFromEnv` 只接受**恰好声明一个**环境变量的 provider，注释说明 Bedrock、Vertex 这类多环境变量的 provider 混有 region/project 等配置，仍需 `-k` 或已保存设置。

这些都只影响宿主如何判断「这个 provider 配好了没有」，不改变凭据从哪里读、请求怎么发，因此不新建 custom_providers 版本。本轮不为此写引用——没有新章节消费它们，写下未引用的引用只会成为数据集里的孤儿记录。证据定位（文件、行号、提交）记在本审计的 `investigation_notes` 里，供下一轮需要改写时直接取用。
